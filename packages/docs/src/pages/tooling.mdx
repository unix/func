`func` is the command runtime; `funcgo` is its project tool. It does three jobs: inspect package configuration, execute a TypeScript entry for local development, and bundle that entry into an executable production directory. It does not decide your command model or generate application help.

  <Callout title="Development-only tooling" variant="note">

`funcgo` is scaffolding and build tooling, so it is not included in the final bundle. Its relationship to `func` is similar to Vite's relationship to React.

  </Callout>

Projects created automatically from the default template already include `funcgo`. For any other project, install it as a development dependency before using the commands on this page:

<CodeBlock
  code={installCommands.npm}
  lang="shell"
  packageManagerCommands={installCommands}
/>

Use the package scripts for the normal path, and invoke `funcgo` directly when you need a custom file, output, external dependency, or watch target.

## Inspect configuration with setup

<Callout title="Read-only by default" variant="note">

`funcgo setup` only reports recommendations. Adding `--fix` authorizes it to update package configuration and conventional script names.

</Callout>

`funcgo setup` reads the current `package.json` and prints missing or differing recommendations. Without `--fix`, it makes no changes.

<CodeBlock code={setupCode} lang="shell" />

`--fix` can write `func.entry`, `func.outDir`, a `bin` mapping, and the conventional `dev` and `build` scripts. Use it for a new CLI package. In an existing application package, review the suggestions first because those generic script names may already belong to the host application.

Setup detects `src/index.ts` or `index.ts` when present. If it cannot find an entry, it recommends `src/index.ts`; create that file before expecting dev or build to work.

## Run TypeScript once with dev

`funcgo dev` starts Node.js with a local TypeScript runtime and executes the resolved entry. Everything after `--` is passed unchanged as the CLI's argument array.

<CodeBlock code={devCode} lang="shell" />

The `-f`/`--file` option chooses a different entry without changing package configuration. `dev` runs once and exits; it does not watch source files. Repeat the command while editing, or use build watch with a globally linked executable as described in the [Quick Start](/guide).

## Create a production bundle

`funcgo build` bundles the resolved entry and its reachable dependencies, writes `index.js` to the output directory, and creates an executable `bin.js` that loads it.

<CodeBlock code={buildCode} lang="shell" />

Use `-f`/`--file` for a custom entry and `-o`/`--out` for an isolated output. Each `-e`/`--external` leaves one package outside the bundle. An external package must still be available to users at runtime, so keep it in package dependencies and include it in the distribution plan.

## Rebuild when inputs change

`--watch` keeps the build process open. It performs an initial bundle, then rebuilds after matching file changes. By default it watches `src/**/*.ts`.

<CodeBlock code={watchCode} lang="shell" />

Repeat `--watch-path` for every additional file, directory, or positive glob. A custom watch path replaces the default set, so include the TypeScript glob explicitly when adding a configuration file. `--watch-path` requires `--watch`. Negative globs are not supported, and the output directory, `node_modules`, and `.git` are ignored to prevent rebuild loops.

## Enable shell completion

Completion is an opt-in subpath. Replace the entry's `run` call with `runWithCompletion` and pass the executable name from `package.json#bin`:

<CodeBlock code={completionEntryCode} filename="src/index.ts" lang="ts" />

Existing command, handler, option, alias, description, constraint, and `@Enum` metadata is reused automatically. No completion-specific decorators or generated command manifest are required. `@Enum` values are offered after value options; otherwise positional input falls back to the shell's file completion.

Load the generated adapter from the user's shell profile. The command prints adapters for Bash, Zsh, Fish, and PowerShell; these adapters query the executable on each completion so they stay aligned with the current command graph:

<CodeBlock code={completionSetupCode} lang="shell" />

For PowerShell, set `$env:_SHIP_COMPLETE = 'powershell_source'`, pipe `ship` through `Out-String | Invoke-Expression`, then remove the environment variable. The variable name is derived from the executable by uppercasing it, replacing punctuation with underscores, and adding the `_COMPLETE` suffix.

The ordinary `func` entry does not export or import completion. Applications that keep using `run` therefore do not make the completion engine reachable to the production bundler. Applications using `runWithCompletion` pay for the metadata query and four small shell adapters, but completion requests compile only the command graph: they do not construct modules, initialize providers, or dispatch handlers.

## Understand resolution order

| Setting       | Highest to lowest priority                                         |
| ------------- | ------------------------------------------------------------------ |
| Entry file    | `--file / -f → package.json#func.entry → src/index.ts → index.ts`  |
| Build output  | `--out / -o → package.json#func.outDir → dist`                     |
| Watch targets | `Every --watch-path → src/**/*.ts when no custom path is supplied` |

Command-line overrides are useful for experiments and secondary entries. Store the normal package contract in `package.json` so local development, CI, global linking, and publishing agree:

<CodeBlock code={packageConfigCode} filename="package.json" lang="json" />

The `bin` key is the command users type; its value must point to the generated `bin.js` inside the chosen output directory. See the [API Reference](/apis) for the compact option list.
