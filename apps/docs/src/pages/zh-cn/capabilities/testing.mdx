func 提供三个主要测试入口。日常命令行为优先使用 `func/testing`，需要进程边界时使用 `func/testing/cli`，需要磁盘项目时使用 `func/testing/fixtures`。`func/testing/pty` 只提供可选的适配数据接口，不包含 PTY 实现。

## 在内存中测试命令

`createTestingApp` 编译一次 module；每次 `invoke` 都会创建新的调用容器、IO 和依赖图，不会启动子进程：

<CodeBlock code={testingCode} filename="tests/deploy.test.ts" lang="ts" />

`invoke` 的第一个参数是省略可执行文件名后的 argv。第二个参数控制本次调用：

| 选项     | 用途                                                    |
| -------- | ------------------------------------------------------- |
| `cwd`    | 设置本次调用的 `Context.cwd`，不会调用 `process.chdir`。 |
| `env`    | 设置完整的 `Context.env`，不会自动继承 `process.env`。  |
| `stdin`  | 作为本次调用的标准输入。                                |
| `signal` | 向命令传递 `AbortSignal`。                              |

  <Callout locale="zh-cn" title="env 必须显式传递" variant="warning">

`invoke` 和 CLI runner 的默认环境都是空对象。测试依赖 `PATH`、`HOME`、CI 变量或凭据时，应传入最小环境；确实要继承测试进程时，显式使用 `{ ...process.env, OVERRIDE: 'value' }`。这样测试不会意外依赖开发机环境。

  </Callout>

`invoke` 始终返回 `{ exitCode, result, stdout, stderr, error }`。已被 `onError` 处理的异常不会出现在 `error` 中，调用也不会修改测试进程的 `process.exitCode`。

  <Callout locale="zh-cn" title="输出必须经过 Context.io" variant="note">

测试应用只捕获 `@Stdout()`、`@Stderr()` 和 `Context.io` 的输出。全局 `console` 仍写入当前测试进程，无法通过 `result.stdout` 或 `result.stderr` 断言。

  </Callout>

## 测试真实 CLI 进程

`func/testing/cli` 从 `package.json#bin` 定位已构建入口，使用当前 Node 可执行文件启动子进程，并捕获 stdout、stderr、退出码和信号：

<CodeBlock code={cliCode} filename="tests/cli.test.ts" lang="ts" />

runner 不会自动构建项目。建议把大多数测试留在内存层，只在独立的 CLI 测试脚本中先构建，再覆盖 package bin、进程退出、启动环境和真实文件系统集成。多 bin package 通过 `binName` 指定入口，也可以直接传 `bin`。

`cwd` 是子进程工作目录；`env` 是子进程的完整环境，两者都应在测试中显式设置。`timeoutMs` 到期时会向子进程发送 `SIGTERM`，并在结果中设置 `timedOut`。

## 对接自行选择的 PTY 工具

普通子进程 pipe 不能验证 `isTTY`、提示符交互和终端尺寸，这类场景属于端到端测试。func 不启动 PTY，也不依赖 `node-pty` 或 Python 运行时。

`func/testing/pty` 仅导出 `PtyAdapter`、`PtyProcess`、`PtySpawnOptions`、`PtyExitEvent` 和 `PtyDisposable` 数据接口。项目可以按自身平台与安装策略用 Python `pty`、`node-pty` 或 ConPTY 实现接口；进程生命周期、输出聚合、等待提示符和清理由项目自己的测试工具负责。

## 推荐的默认测试范式

1. 用 Vitest 和 `createTestingApp` 覆盖命令分发、参数、provider、输出与错误，这是默认且最快的一层。
2. 用 project fixture 覆盖配置文件、生成物和工作目录行为。
3. 用单独的 `test:cli` 脚本覆盖少量已构建 CLI 冒烟测试。
4. 提示符、TTY 检测和终端 resize 等端到端行为，由项目自行选择 PTY 工具并通过可选接口对接。

默认 TypeScript 模板已经提供 Vitest 的 decorator 转换配置，并把内存测试与构建后的 CLI 测试拆成 `pnpm test` 和 `pnpm test:cli`。

## API 速查

| 入口                    | 主要 API                                                |
| ----------------------- | ------------------------------------------------------- |
| `func/testing`          | `createTestingApp`、`TestingApp.invoke`、provider 覆盖。 |
| `func/testing/fixtures` | `createProjectFixture`、`withProjectFixture`。           |
| `func/testing/cli`      | `createCliRunner`、`CliRunner.run`。                     |
| `func/testing/pty`      | 仅提供 backend-neutral 的 PTY 适配数据接口。            |
