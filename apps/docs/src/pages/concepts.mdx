`func` takes strong inspiration from Angular and NestJS. Its goal is to give command-driven applications a consistent, loosely coupled, maintainable, and dependable architecture.

Most applications do not need to know how each invocation is wired internally. Declare a uniform application structure, the commands it supports, and the services those commands need; the framework organizes and connects the pieces.

Building a command-driven application with `func` is therefore much like building a conventional web application. Once the design model is familiar, most work stays at the application layer and developers can focus on business behavior instead of framework mechanics.

## Architecture overview

A `func` application centers on four ideas:

1. **Application:** the composition root for every participating command and Provider.
2. **Command:** a user-facing entry that describes a concrete capability of the application.
3. **Provider:** reusable business or infrastructure functionality such as data access, external services, and domain logic.
4. **Dependencies:** Commands declare the capabilities they require rather than constructing or connecting them. `func` resolves those declarations and assembles them at runtime.

## Definitions and invocations

Commands are the basic unit for organizing CLI capabilities. One Command class may contain field options, one or more Handlers, and Provider dependencies needed by the business operation.

For each invocation, `func` matches the complete input to one command node and selects exactly one Handler. Multiple Handlers on a Command class are alternative entry points—not steps that execute in sequence.

A Command may expose a default action, path actions, and flag actions, but only the action selected by the current input runs. That Handler sees already parsed and validated input and can call injected Providers to perform its work.

<CodeBlock code={conceptModel} filename="Func mental model" />

The Module first registers the Commands and dependencies that define the application. When an invocation arrives, `func` chooses the matching Command and Handler, then supplies the target method with input and the capabilities it needs.

For a quick working model:

- A Command organizes CLI capabilities.
- A Handler performs one action, using the supplied input.
- Providers implement the business behavior.

## Application: the complete program

An Application is a set of commands and internal capabilities that can run together; it does not correspond to one CLI path. The root Module (`app.module.ts`) is its definition entry. From there, `func` discovers the Commands, Providers, and shared features and compiles them into an invokable application.

The same Application definition may start as a CLI process or be invoked programmatically by another process. Both entry modes share Commands, input rules, and Providers; only the source of the invocation differs.

## Command: the invocation entry

A Command is the main user-facing unit of organization in `func`, represented by a class with a Command decorator. It commonly corresponds to one business domain or a group of closely related tasks, such as `project`, `config profile`, or `deploy`.

A Command path is fixed syntax that users must enter. It may contain one or several segments, and multiple Commands may share path prefixes. `func` compiles Command and Handler paths into a command graph, then selects the unique executable node with the most complete match.

### Command variants

Most business operations use named commands. Major and missing commands are optional special entries for invocations that do not select a named command:

| Entry         | Selection condition                                                   | `func` API             |
| ------------- | --------------------------------------------------------------------- | ---------------------- |
| Major command | No named path matched; its default or path Handler can execute.       | `@CommandMajor()`      |
| Named command | Positional tokens longest-match a Command path plus a Handler path.   | `@Command('<name>')`   |
| Missing command | No named path matched and positional input remains unconsumed.      | `@CommandMissing()` (optional) |

<Callout locale="en" title="Command paths may share prefixes" variant="decision">

`ship project member add` can be modeled as `@Command('project')` plus `@Handler(['member', 'add'])`, or by another class declaring `@Command(['project', 'member'])`. `func` builds one graph and chooses the unique longest executable match.

</Callout>

## Handler: the executable action

A Handler is the method on a Command class that actually performs an action. It is declared with `@Handler()`, and one Command may provide several.

There are three ways to select one:

- **Default Handler:** has no path or flag and runs when no other action is selected at the current command node.
- **Path Handler:** extends the command path with fixed positional tokens such as `member add`.
- **Flag Handler:** switches to a mutually exclusive action through an option such as `--version`.

An invocation ultimately runs one Handler only. Declaring several methods in a Command class never makes them execute sequentially. A Module-level `@OptionCommand()` may also provide a cross-command action such as `--help`; it likewise replaces the current business action instead of running alongside it.

<Callout locale="en" title="Similar terminal syntax can have different roles" variant="decision">

A `--force` declared with `@Flag()` supplies boolean data to the selected action. `@Handler({ flag: 'version' })` and `@OptionCommand({ name: 'help' })` select a different action. All begin with hyphens at the CLI, but they model different responsibilities.

</Callout>

The key distinction between a Handler path and positional data is whether the token belongs to fixed grammar. `member add` is an action path declared by the developer; `alice` is business data that varies with each invocation.

## Input: data for the action

Field options and positional input answer the question, “What data should the current action use?”

### Field options

Field options are named inputs declared on a Command or option Provider property. `func` recognizes names and aliases, converts types, assigns properties, and runs validation. The Handler reads the final values directly.

| User data                            | Example                           | `func` API                         |
| ------------------------------------ | --------------------------------- | ---------------------------------- |
| Boolean state                        | `--force`                         | `@Flag()`                          |
| One string or number                 | `--role owner`, `--port 3000`     | `@Value()`                         |
| Repeated strings or numbers          | `--include src --include tests`   | `@ArrayString()`, `@ArrayNumber()` |

Field options suit data with a stable name, type, default, or validation rule. See [Field options](/options) for the declaration syntax.

### Positional input

Positional input has no option name; its meaning comes from its position. Once Command and Handler paths have matched, remaining positional tokens are available from `@Args().inputs`. `alice` in the example is not fixed grammar, so `addMember()` receives it as positional input.

This form works well for file paths, search terms, usernames, and other dynamic values. `@Args()` also exposes canonical paths, the path actually invoked, and a normalized option snapshot. See [Parameters and context](/parameters) for those runtime values.

## Provider: reusable capabilities

Providers typically encapsulate domain logic or infrastructure such as services, repositories, configuration, and external API clients. They let Handlers orchestrate an invocation without constructing dependencies or implementing every detail themselves.

In the example, `ProjectCommand` understands `project member add` and its input, while `ProjectService` owns the actual member-management capability. A constructor dependency connects the two: the Command declares that it needs `ProjectService`, and `func` creates and injects the instance at runtime.

This separation has practical benefits:

- Different Commands and Providers can reuse the same service.
- Commands focus on input and orchestration while business logic remains independent.
- Dependencies can be replaced for tests or as infrastructure evolves.
- The framework coordinates lifecycle and resource cleanup consistently.

Classes decorated with `@Injectable()` are the most common Providers, though fixed values and factories can provide tokens as well. At this stage, think of a Provider as a capability supplied by the application and managed by the framework.

<Callout locale="en" title="Not every concept corresponds to an input token">

`@Module()` and `@Injectable()` organize application code without representing CLI tokens. Commands, Handlers, and input describe how users call the application; Modules and Providers describe how its capabilities are assembled internally.

</Callout>

## Put the concepts together

For `ship project member add alice --role owner --force`, `func` performs these responsibilities:

1. `project` selects `ProjectCommand`.
2. `member add` selects the `addMember()` Handler within it.
3. `--role owner` and `--force` are parsed, converted, and bound to Command fields.
4. `alice` appears in `@Args().inputs` as remaining positional input.
5. `ProjectService` is constructed and injected according to the Command's dependency declaration.
6. After validation, only the selected `addMember()` entry runs.

That is the central collaboration model in `func`: **Commands divide user-facing capabilities, Handlers represent concrete actions, field options and positional input supply data, Providers carry reusable capabilities, and Modules compose those declarations into an application.**
