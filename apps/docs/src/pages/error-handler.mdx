func uses exception filters for cross-cutting failure handling and keeps `onInit` and `onDispose` focused on resource lifecycle. Command and module `onError` methods are no longer part of the runtime model.

## Exceptions and defaults

Application code may throw native errors or the public `Exception` class. `Exception` exposes stable `code`, `scope`, `details`, `message`, and `cause` fields, but it does not define a JSON wire format.

Correctable CLI input failures and ordinary handler errors set exit code `1` and use a minimal one-line stderr route by default. The fallback does not add color, tables, or other UI. Definition failures and provider initialization failures continue to escape unless an application filter explicitly handles them.

Error scopes are `F_SYSTEM` and `F_RUNTIME`; the former `F_RUNTIME_PRINT` scope is now part of `F_RUNTIME`.

## Command filters

`@Catch()` matches every exception. It can also receive an `ErrorScope`, a complete error code, or an Error class. Bind a filter statically with `@UseFilters()`:

Returning handles the failure. Throwing continues with the next outer filter. A filter may write directly to stdout or stderr as an escape hatch for custom UI, but its normal role is matching, routing, and producing structured results.

## Module and application scope

Register DI-managed filters through multi-provider tokens:

- `MODULE_FILTER` applies to the direct owner module.
- `APP_FILTER` is application-wide wherever its provider is declared, including parse failures with no selected command.
- Order is command, owner module, application, then the func fallback.

<CodeBlock code={moduleFilterCode} filename="src/app.module.ts" lang="ts" />

Filter classes are created by DI and can inject visible providers, `Context`, and managed streams.

## Returning JSON error data

func does not define an error JSON schema or serialize `Exception` automatically. Return an ordinary value from a filter. An imported `JsonOutputModule` handles it through the same result chain as a handler return:

## Lifecycle

`onInit` and `onDispose` remain resource lifecycle hooks:

<CodeBlock code={lifecycleCode} filename="src/app.module.ts" lang="ts" />

`onDispose()` receives no invocation result and its return value is ignored. Activated commands, modules, and providers are released in reverse order. If a hook throws or rejects, Runtime reports the lifecycle fault, continues the remaining hooks, and preserves the settled result, exit code, and output. Lifecycle faults do not enter exception filters.
